# Airlock design

Airlock lets you reach this laptop from your phone over Tailscale: what needs you ("Home"), terminals, your projects and Claude Code sessions ("Work"), files, system status and dev-server previews. A laptop app shows the phone's terminals and sessions, keeps two weeks of their history, and is the only place that can approve devices and edits made on the phone.

This is a design document: it records what is being built and why. The build order at the end says which parts exist.

## Goals

- One place on the phone to see and drive the laptop: terminals with tabs, Claude Code sessions by repo, files, processes and ports.
- A laptop app that shows the same things and holds the authority: approving devices, approving file edits made on the phone, revoking devices, settings.
- Nobody but you gets in, and a stolen phone or a copied cookie stops working fast.
- Themes on top of one UI, added after the build.

## Non-goals

- Gating the terminal. The phone's terminal is a real shell with no approval step; approvals cover only file edits made outside the terminal.
- Git workflows from the phone. Work shows branches, worktrees and PRs; it doesn't check out, create PRs or make worktrees.
- Reaching the laptop from outside your tailnet.

## Architecture

```
 phone (Safari)                          laptop
 web UI ──HTTPS──▶ Tailscale Serve ──▶ hub  (Rust, user service)
                   :443, tailnet only   ├─ phone server, 127.0.0.1:7690
                                        ├─ terminals: hub-owned PTYs → tmux -L airlock
                                        ├─ work (projects, sessions), files, system, dev servers
                                        ├─ SQLite: devices, pairings, changes, audit, history
                                        └─ admin socket, $XDG_RUNTIME_DIR/airlock/admin.sock (0600)
                                                  ▲
                                   laptop app (Tauri) and the `airlock` command
```

- **hub** (`hub/`): one Rust binary, `airlock`. `airlock serve` runs the phone server and the admin socket; the other subcommands talk to the admin socket.
- **UI** (`ui/`): one web frontend for the phone and the laptop app, in Svelte and TypeScript, built with Vite into `ui/dist` and embedded in the hub's binary. Themes restyle this one UI, with their own header and terminal list. The phone keeps the files in `assets/`, named by a hash of what's in them, for a year, and asks again only for the page that names them; xterm and highlight.js, two thirds of the code, load the first time a terminal or a source file opens. The hub compresses what it sends (brotli, else gzip, at level 4, quick enough for every poll), except streamed answers and images, since Tailscale Serve passes it on as it is. A main screen's data is kept between visits, so coming back shows it at once while it refreshes.
- **laptop app** (`app/`, binary `airlock-app`): Tauri, so it uses the system WebKit, the same engine as the iPhone. It talks to the hub only through the admin socket, using the same client as the `airlock` command. Its window may call only the app's own commands, as its capability file grants: admin calls (pairings, approve, deny, devices, revoke, activity, terminals, sessions, history), and the app's own terminal screens (`app/src/screens.rs`), each a tmux client in a PTY the app owns, attached to the hub's tmux server, its bytes sent to the window over a Tauri channel. The window freezes `Object.prototype` itself once its modules have loaded (`ui/src/laptop/main.ts`), not through Tauri's `freezePrototype`, which runs before them and breaks xterm. It follows the admin socket's event stream (`GET /events`, one JSON event per line), raises desktop notifications from it, and lives in the tray so they keep coming with the window closed. Its CSP allows inline styles, which xterm.js needs.
- **Files on disk**: secrets and settings in `~/.config/airlock` (mode 700), the database in `~/.local/state/airlock` (mode 700), the admin socket in `$XDG_RUNTIME_DIR/airlock` (mode 700, socket 0600).

## Security model

Two doors, never mixed:

- **The phone door** is the phone server behind Tailscale Serve. It listens on loopback only. Every request must carry a `Tailscale-User-Login` header naming a login in `allowed_logins`; Serve adds that header for your own devices. Requests that change anything, and websocket upgrades, must come from the hub's own origin. Every response carries a strict Content-Security-Policy, `X-Frame-Options: DENY`, `nosniff`, `no-referrer` and `no-store`, except what never changes under its address: the UI's files named by their content's hash, and a thumbnail named by its file's modified time.
- **The laptop door** is the admin socket, a Unix socket only your user can open. Approving pairings, revoking devices, approving file edits and settings exist only here, so nothing on the phone side can approve anything.

Devices:

- **Pairing.** A new device asks to pair and shows a six-digit code. The laptop approves it by that code. Requests expire after 5 minutes and at most 3 wait at once. The approved device receives a device token in an `HttpOnly; Secure; SameSite=Strict` cookie.
- **Rotation.** A device token is replaced with a fresh random one after 10 minutes of use. The old token keeps working until the device uses the new one, then it is retired. A retired token coming back means it was copied: the hub revokes the device on the spot, closes its connections, logs it, and alerts the laptop app. A replacement the device never received is overwritten, not treated as theft.
- **Expiry and revocation.** A device unseen for 30 days has to pair again. Revoking a device from the laptop closes its live connections at once.
- **Storage.** Tokens and pairing secrets are stored only as SHA-256 hashes, so reading the database never lets anyone in.
- **Face ID.** Once paired, the phone offers to register a passkey (WebAuthn, verified by the hub with `webauthn-rs`; user verification required). A device with a passkey is locked unless the request also carries a live unlock cookie: unlocking with the passkey hands that browser a fresh random secret (kept by the hub only as a hash, in memory), which dies after 5 minutes without a request (`face_id_lock_secs`), or at once when the phone leaves Airlock: the page asks the hub to forget it (`POST /api/faceid/lock`) as it is hidden, and shows the lock screen before iOS takes its app-switcher snapshot. A terminal stream belongs to the unlock of the browser that opened it: it ends (close code 4003) within 5 seconds of that unlock dying, and at once when the phone locks, while typing into it keeps the unlock alive. The unlock belongs to the browser that unlocked, not to the device, so a copied device cookie gets nothing even while the phone is unlocked. Each unlock has its own challenge, so an old answer can't be replayed, and the passkey's signature counter is kept. After the hub restarts, every Face ID device starts locked. The passkey's private key never leaves the phone.
- **Audit.** Every pairing request, decision, pairing, revocation and theft detection is written to the audit log (`airlock log`).

What this doesn't protect: a shell on the laptop running as you can reach the admin socket, so once the phone has a terminal it is fully trusted. The approval queue for file edits is a review step, not a wall. The protection is in who can get a session at all.

## Decisions

- **Rust for the hub.** It sits in front of a shell, so memory safety and one static binary matter. Alternatives: Go (not installed here, otherwise a fine fit), Python or Node (more runtime to keep patched).
- **Tauri for the laptop app.** Small, uses the system WebKit like the iPhone, and its Rust side talks to the admin socket. Alternative: Electron, which ships its own Chromium (around 150 MB); kept as a fallback if WebKitGTK gets in the way.
- **The app raises the alerts, from the tray.** Notifications come from the app's Rust side, so the window needs no notification permission, and the tray keeps the app running with its window closed. Alternative: the hub sending notifications itself, which would put a desktop session dependency into the service that faces the phone.
- **Pairing approved on the laptop, instead of a secret URL.** The old phone terminal used a secret path as its only key; anyone with the link got in. Pairing ties access to a device you approved and can revoke. Alternative considered: Tailscale identity alone, which would let in any of your devices, including ones you lend out.
- **Rotating tokens with reuse detection, instead of long-lived tokens.** A copied token is useful for minutes and gives itself away when used. Alternative: short-lived tokens without reuse detection, which expire a thief's access but never tell you.
- **SQLite for state.** One file, transactional, no server. Alternative: JSON files, which don't do concurrent updates safely.
- **Svelte for the UI.** It compiles to small plain JavaScript, which matters on a phone over a tailnet, and a component per screen keeps the many views manageable. Alternatives: React (a larger runtime for the same result), or growing the old single-file page (no types or tests, and already hard to change).
- **GNOME Terminal's tabs shared through a pass-through, not moved into tmux.** You wanted to keep using your tabs as they are, and reach them from the phone. A tab can't be reached from outside once it's open: the kernel refuses to type into another program's terminal (`dev.tty.legacy_tiocsti` is 0), `ptrace` is limited to children, and GNOME Terminal offers no way to read a tab. So the shell has to start inside something Airlock can reach. A pass-through leaves the tab exactly as it was: the terminal's own scrollback, selection and title, and closing the tab ends it. Alternatives:
  - **Starting every tab in a tmux session.** That changes the tab: tmux's scrollback and selection, and sessions that outlive their tabs.
  - **Reading tabs through accessibility, or pasting into them through GNOME Terminal's actions.** Neither can press Enter or Ctrl+C, and pasting takes over the clipboard and the visible tab.
- **The hub owns each terminal's PTY and runs a tmux client in it**, instead of fronting ttyd. Screens attach and detach without the terminal noticing, and the hub's own pairing and origin checks guard the stream. Alternative: ttyd, the old setup, which puts a second web server with its own access rules in front of the shell.
- **Edits approved by writing the file only if it hasn't changed since the phone saw it**, with a conflict view otherwise. No git involvement.
- **Previews on their own origin, not under a path.** A previewed app runs its own scripts; on Airlock's origin it could call Airlock's API with your cookies, and its absolute URLs (`/src/main.ts`) wouldn't work under a path prefix anyway. A second listener, published by Tailscale Serve on another port, is another origin: Airlock's origin checks refuse anything it tries to change, and with no CORS headers it can't read Airlock's answers. Alternatives: a path-prefix proxy (unsafe and breaks most dev servers), or exposing each dev server through Tailscale Serve as it appears (reconfigures the network at runtime).
- **A theme lays out the terminal list, not every screen.** Each theme's mock is its terminal list, so that screen and the main headers follow the mock, and the other screens (Home, a file, a diff, a session) keep one layout in the theme's colours and type. Alternative: a layout per theme for every screen, nine times the screens to keep working, for views seen less often.
- **Home is what needs you, not the terminal list.** Opening Airlock is mostly about what changed while you were away: a prompt, a finished session, a failing check. One screen that gathers those, most pressing first, beats visiting each section. Alternative: badges on each section, which say something is waiting but not what, and leave the terminal list as the first screen.
- **Unlock state per browser, not per device.** Tying "unlocked" to the device would let a copied device cookie ride along whenever the real phone is unlocked. Alternative: per-device unlock, simpler, but it weakens Face ID to "the phone was unlocked recently".
- **History in the hub's database, read by the laptop app.** The hub already sees every terminal and session, so it saves them (every 30 seconds, and as a terminal closes) and forgets them two weeks after they were last active. Alternative: the app recording what it sees, which would miss everything that happened while it wasn't running.
- **The game's levels stitched from hand-made chunks, not grown from noise.** A noise or grammar generator makes endless levels that all feel alike, and nothing in them is placed on purpose. Each level is instead a paced run (a calm start, a build-up, the zone's twists, a checkpoint, a harder stretch, the flag) of set pieces chosen from a library of over a hundred hand-made chunks, raised or lowered, maybe mirrored, with their bug slots filled from the zone's own roster; chunks don't repeat within a level and are avoided across a zone. Zones after the tenth draw two or three twists from a pool, never one the zone before had, along with their own scenery, song and boss. Everything is derived from the seed, the zone and the hop, so a save is small, and the tests check with the game's own physics that every chunk and a sample of whole levels can be finished, small or big, with no place to get stuck. Alternatives: pure procedural generation (cheap, and repetitive), or a fixed set of levels (ends).
- **The game's music and sounds synthesized in WebAudio, not shipped as files.** Each zone's song is written out from a short motif in its key, mode, tempo and groove, so there is a song for every zone without a file for each, and the voices change with the theme (Game Boy pulses, a home computer's filtered saw, an FM organ for the workstation). Notes are scheduled a fraction of a second ahead from the frame loop, which stops when the game does. Alternatives: audio files (a download per song, and the same tune in every theme), or a music library (a dependency for a hidden feature).
- **The game loaded on first open, as its own chunk.** Most people never open it, so the main bundle carries only the long press, the keyboard code and the place it appears; the game (about 48 kB gzipped) downloads the first time it's opened. The CSP needs nothing new: it draws on a canvas and makes sound with WebAudio, with no workers, `eval` or data from elsewhere. Alternative: bundling it with the rest of the UI, a cost on every load for something seldom used.
- **A second game, a story with companions, not more of the platformer.** Keepalive is top-down, so companions can walk with you, stand beside you to talk, and each bring a move that works on the world (freeze, force, hover, talk), and puzzles come from combining them. Alternatives: companions in Hop Count (a platformer's run leaves no room to talk), or a text adventure (no play between the words).
- **Keepalive's story in a small script, not in code.** Scenes, choices, conditions and effects are lines of text (`who: words`, `> choice -> label ~ +flag cron+1`), parsed when a chapter loads, so writing a scene is writing the scene, and the tests can walk every one of them: every label reached, no choice into nothing, every ending reachable. Alternatives: dialogue as TypeScript objects (noisy to write, as large), or an existing format such as Ink (a runtime to ship for a hidden feature).
- **Keepalive's chapters in chunks of their own.** The engine, renderer and hub town are about 58 kB gzipped; each chapter's places and script another 5 to 6 kB, fetched while you play the chapter before. Alternative: one chunk of about 85 kB, all of it downloaded before the first line.
- **Keepalive's rooms checked by a solver, and its story by playing it.** A breadth-first solver over each room's tiles, blocks, signals and abilities proves every room can be cleared with what you have by then, and not without the ability it's built for, and a walker plays the whole story with kind, cold and random choices to each ending. Alternatives: hand-written checks for each room, or only playing it, which misses the room that softlocks on the fourth try.
- **Keepalive's words in the page, its world on the canvas.** Dialogue, choices, menus and the map's card are HTML over the canvas: read at the phone's own size, in the theme's fonts, with real buttons for the keys, the case and screen readers. Alternative: pixel text in the canvas, small on a phone and a font per theme.
- **One way in to both games, with a card to pick.** The long press and the code stay the only doors, and the card lists the game played last first, so going back to it is one more tap. Alternative: a door of its own for the second game (another gesture to find and remember).
- **Polling, with news pushed for sessions.** Each screen asks for what it shows while it's visible (`ui/src/lib/polled.svelte.ts`): the next ask a while after the last answer, so a slow one never piles up requests; the latest ask's answer wins; nothing while the page is hidden, and at once when it comes back if one is due. The hub pushes one kind of news on `/api/events`: that a Claude session changed how it stands (`sessions_changed`, saying neither which nor how), on which Home, Work and a session's screen ask again at once, so a prompt shows the moment it comes and those screens poll only every 10 seconds. When the hub ends that connection (the phone was revoked, or the hub is stopping), they ask again at once too, so a revoked phone is back at pairing within a moment. Alternatives: pushing every change with its data (a push for each screen's data, and the hub tracking what each phone shows), or polling alone (a prompt waits for the next poll, and the polls come often).
- **Ask Claude through Claude Code, not the API.** `claude -p` runs with the login you already have, so Airlock keeps no API key, and it brings the tools to look around: reading files, searching, running commands. Claude Code's own permission rules make it read-only: a fixed list of tools, `dontAsk` so anything off the list is refused rather than asked about, Bash only for commands that read, and deny rules for the files that hold secrets. Alternatives: the Messages API (a key in Airlock's config, and tools of Airlock's own to write and keep safe), or a Claude Code session in a terminal (it could change things, and it would show up among your sessions).
- **Signals through a pidfd.** Checking a process's start time and then calling `kill` leaves a moment in which the pid can be reused; a pidfd opened before the check names that one process, so the signal can't reach another. Alternative: `kill` after the check, simpler, and safe only most of the time.

## Features

- **Home** (`attention.rs`, `GET /api/attention`): the phone's first screen, everything that needs you in one call, each thing with a level (`act`, `look` or `fyi`) and an id that stays the same while the thing does, so the phone can hide one until it changes. It is built from what the hub already reads for Work and System, through their caches: sessions from the hooks, processes and ports looked at no more than every 15 seconds (with a sampler of its own, so the System screen's CPU readings stay its own), units from their 5-second cache, and pull requests only once read (the list asks `gh` for each one's check rollup and review decision; Home never waits on GitHub). The same call lists every Claude session going on and those ended in the last hour, waiting on you first, then working, then done. A session that is done can still have something running (`background.rs`): a command Claude Code left in the background, found among the Claude process's descendants by the shell wrapper Claude Code runs commands in (`eval '<command>' < /dev/null`, after sourcing its shell snapshot), and its agents, from the session's `subagents/agent-*.jsonl` written in the last two minutes, named by their `.meta.json`.
- **Terminals**: terminals with tabs, on the hub's own tmux server (`tmux -L airlock` by default, set by `tmux_socket`): a terminal is a tmux session and a tab is one of its windows. The tmux server is the hub's child, in its service's control group, so the unit stops the hub alone (`KillMode=process`): a restart, for an update or after a crash, leaves the terminals and what runs in them, an update started from the phone included, and the new hub finds the server again. `install.sh` keeps the hub from before and puts it back if the new one doesn't answer on the admin socket within 15 seconds. Tab names, gestures and the phone key bar carried over from the old phone terminal (ttyd), which Airlock replaced; the key bar holds no personal paths (Go to… picks a folder and types the `cd`). The phone checks its link when it comes back from the background and reconnects if iOS left it dead. Streams don't pile up: the hub pings each every 20 seconds and ends one that hears nothing for 60; a device's new stream to a terminal replaces its old one (close code 4001, which the phone doesn't retry, so two tabs don't trade it forever); and a device has at most 6 open. A stream whose terminal closed ends with 4004, and the phone goes back to the list. The phone connects only once its screen has its size, so what arrives first is drawn at the width it is shown at.
- **Laptop tabs** (`laptop_tabs.rs`, `tab.rs`): GNOME Terminal's own tabs, on the phone as they are.
  - **The pass-through:** a block at the top of `~/.bashrc` (`airlock tabs install`) runs the shell of each new tab inside `airlock tab`. That's a pass-through: the shell in a PTY of its own, every byte handed to the terminal unchanged and the terminal put in raw mode, so keys like Ctrl+C reach the shell's own terminal.
  - **What reaches the hub:** each tab streams to the hub over a websocket on the admin socket. The hub keeps its screen in a `vt100` parser, and the phone streams it like a terminal.
  - **Opening a tab on the phone:** the phone first gets the screen as lines of coloured text, with no cursor moves, so it wraps at the phone's width; then it gets what the tab prints.
  - **Size:** whoever typed last sets the tab's size, as tmux does. While a phone has it, the hub's copy of the screen keeps its width, so no line is cut.
  - **Never in the way:** the pass-through never waits on the hub. Without one it works alone and tries again every 10 seconds. A hub that falls 512 chunks behind is let go. If it can't start, it becomes the shell itself.
  - **The close warning:** GNOME Terminal asks before closing a tab whose foreground process group isn't the process it started. That process is now the pass-through, which would always look idle. So while a program runs in the shell (checked every 250 ms: the shell's terminal's foreground group isn't the shell), a keyboard helper (`airlock tab-keyboard`) in a group of its own holds the terminal's foreground and passes the keys on, and GNOME asks as before. Back at the prompt, the keyboard returns.
    - **How the hand-over works:** the pass-through reads the terminal only through readiness, never a blocking read, so it can stop at once. Each hand-over is acknowledged (signals there, a byte back), so one reader at a time takes keys from the terminal's queue, in order.
    - **Resizes:** the helper passes window resizes, which go to the foreground, back to the pass-through.
    - **If the helper fails:** if it dies or doesn't answer within a second, the pass-through takes the keyboard back and goes on without it.
- **Work** (`center` in the code and routes): Claude Code sessions by project, grouped by project root (`project_roots`: each folder directly inside a root is a project, repo or not; a session counts for the one project folder it is in), then worktrees and what's active in each. "Needs you" on top, answered by typing into the session's terminal. Branches and PRs are view-only, with Full diff and Open on GitHub. Sessions report through Claude Code hooks (`airlock hooks install`): each runs `airlock hook` asynchronously, which trims the event to the session, folder, tool and a few input fields (never file contents or tool results) and passes it to the admin socket. The hub keeps sessions in memory and saves the ones going on to its database every 30 seconds and as it stops; when it starts, it takes back each one whose Claude process, named by pid and start time, still runs. A session waiting at a prompt reports nothing until it's answered, so without that it would vanish at every update while it still waited. Git runs read-only with `GIT_OPTIONAL_LOCKS=0`, so it never takes the index lock. A repo's status is read again once it's 4 seconds old, in the background, once however many ask, while the last one is shown (up to a minute old), so a poll never waits on git; pull requests come from `gh`, cached for two minutes.
- **A session's terminal and steps**: the hook reports the Claude Code process's pid, and the hub finds the terminal it runs in: an Airlock tab, another tmux pane, a shared laptop tab (its Claude is a descendant of the tab's shell), or another terminal app. In tmux or a shared tab, the phone shows its screen in colour and types into it (text, or a key from a short allowed list), and prompts are answered there (`answer::Reach`: a tab's screen comes from the hub's parser, and keys go in as the bytes a terminal sends, arrows in the cursor-key mode the program set); elsewhere, Share with the phone asks that Claude to quit (SIGTERM, through a pidfd, after checking it is still a Claude process), waits up to 5 seconds for it to exit, and runs `claude --resume <id>` in a new Airlock terminal; the hub sends `session_shared`, and the laptop app opens that terminal in a Terminal window, so the session is on the laptop and the phone at once. It refuses while the session is working, and checks the folder before anything is quit. Continue here does the same for a session nothing runs any more, and the hub refuses it while a Claude still does: two on one conversation would each carry on from the same point and diverge. A session whose Claude process has gone counts as ended. Each step has a number, and opening one reads the session's transcript (`$CLAUDE_CONFIG_DIR` or `~/.claude`, `projects/*/<id>.jsonl`, found by the session's id) for that tool call, by its id, or by name and input for an older step: the full input, an edit as a diff (`similar`), and what the tool gave back, cut at 60,000 characters. The hub keeps nothing it reads there.
- **History**: every 30 seconds the hub saves each open terminal's tabs (their last 2,000 lines, colours kept) and each session's steps to its database. A terminal or session that closes or ends stays there for 14 days after it was last active and is then deleted; the laptop app deletes one sooner on request. Only the laptop app reads it, through the admin socket.
- **Answering a prompt from the phone**: the hub reads the prompt off the session's tmux pane, finds the chosen option by its words ("Yes"; a "Yes, …" that isn't a switch of mode; Deny is Escape), moves the highlight to it and presses Enter. With no prompt on screen it types nothing. This was checked against a real Claude Code 2.1.301 session.
- **System**: resources, listening ports and who can reach them, background jobs and the busiest processes; every process (`procs.rs`), with CPU history kept by the hub's sampler for the last 30 looks, its kind from its cgroup (the scope the desktop started an app in, a GNOME Terminal tab, a service), and a note on what it is from a short built-in list, the app's desktop entry or the service's description, and, when opened, the package that installed it (`dpkg -S`); and services and timers, yours and the system's (`units.rs`, from `systemctl show`). For a failed service, the phone asks why when it is opened, never with each refresh: systemd's `Result` and exit status, the last 15 lines of its journal (`journalctl -o cat`), and the package that owns its init script or unit file (`dpkg-query -S`). Each command gets 3 seconds, and only a service the list shows can be asked about. The plain explanation and verdict for the common ones are the phone's (`services.ts`). Stopping anything asks first, and a process that ignores the polite stop is only forced after a second confirmation; the hub holds to that too, forcing only a process it asked to stop in the last ten minutes. The hub reads `/proc` itself (listening sockets from `/proc/net/tcp*`, matched to your processes through their socket inodes); a stop names the process by pid and start time, and the hub opens a pidfd for it before checking that start time and signals through it (`pidfd_send_signal`), so a reused pid is never hit. Whether it stopped comes from the pidfd turning readable. Only your own processes and user units can be stopped, never the session's, the hub or Airlock's tmux. Each listening port gets a kind, an owner and a verdict (`ports.rs`). Its kind comes from your process's name, from the image of the Docker container that publishes it, or from the port number for the system's. The containers come from `docker ps`, asked at most every 30 seconds and given 3 seconds, since Docker's proxy runs as root and its sockets can't be matched to a container. The verdict follows from who can reach it: only the laptop or the tailnet is safe, a database open to other networks is a worry, and anything else open is worth a look. The phone words it all and adds the firewall's state, read from `/etc/ufw/ufw.conf`. A container is stopped with `docker stop`, only one running now that publishes a port, and the stop is audited.
- **Files**: browse and read inside `files_root` (your home by default), paths resolved through symlinks and kept inside it, Airlock's own folders never shown. Markdown is rendered by the hub with raw HTML escaped, links limited to the web, mail and other files, and images to local ones (no tracking pixels). HTML is served with a `sandbox` CSP and shown in a sandboxed frame, so it can't run scripts or reach Airlock. Sensitive files are readable while the laptop's `sensitive_files` setting allows it (on by default). A folder shows as a list or a grid, sorted on the phone; the grid's thumbnails are the images themselves, only for those up to 3 MB and never sensitive ones, and the browser keeps one while the URL's `v` still matches the file's modified time.
- **Edit queue**: the phone sends the text it read and the text it wants; nothing is written then. The laptop app shows the diff and writes the file only if its SHA-256 still matches what the phone read (written beside it, then moved into place, keeping its permissions). Otherwise it shows both changes and offers a three-way merge (`git merge-file`) when they don't overlap, the phone's version (an explicit overwrite), or keeping the laptop's.
- **Notifications** (`push.rs`, `ui/public/sw.js`, `ui/src/features/notifications/`): Web Push. The phone, opened from its Home Screen (iOS allows pushes only there, from the web app manifest's `standalone` app), subscribes through its push service with the hub's public key (`GET /api/push/key`) and hands the hub the address and keys (`POST /api/push/subscribe`), kept per device and dropped with it. When a hook moves a session to waiting on you, or from working to done, the hub signs a push with its own P-256 key (VAPID, RFC 8292; `~/.config/airlock/push.pem`, mode 600, made on first start) and encrypts it to the phone's keys (`aes128gcm`, RFC 8291, checked against the RFC's example), so the push service carries it without reading it. It says only what happened and the terminal's name or the folder, never the command or the question, since it shows on the lock screen; one per session at a time (its tag), and tapping it opens the session. A subscription its push service calls gone (404, 410) is forgotten. The service worker shows notifications and nothing else: it caches nothing and sees no other request. HTTPS to the push service goes through `reqwest` on the system's OpenSSL, which the hub already linked for passkeys.
- **Ask Claude** (`ask.rs`, `POST /api/ask`, `ui/src/features/ask/`): a question, what it's about (the screen's facts, in words) and the conversation so far go to `claude -p` in your home folder, and its answer streams back as it comes, one JSON event per line (`text`, `looking` for each tool it calls, `done`, `error`), read from Claude Code's `stream-json` output with partial messages. It runs with `--restricted`, no MCP servers (`--strict-mcp-config`), no saved session, `--permission-mode dontAsk`, the tools Read, Grep, Glob, Bash and WebSearch, Bash allowed only for the read-only commands in `READ_ONLY` (a rule matches every command that starts with it, so a command with a flag that writes, like `git diff --output`, is left out or allowed only whole), and deny rules for Airlock's config, `~/.ssh`, `~/.gnupg`, Claude Code's credentials, the keyring and `/proc/*/environ`. An ignored test asks the real Claude Code to look and then to make a file (`cargo test -p airlock ask -- --ignored`). `AIRLOCK_ASK` in its environment makes `airlock hook` ignore it, so it never shows as a session. The model is one of `MODELS` (`GET /api/ask/models`), Sonnet 5.5 unless the phone picked another. Each answer gets 3 minutes and the process is killed when the phone stops reading; two run at once at most, and the question, what it's about and the conversation are capped in size. It adds nothing a phone could not already do: the phone has a terminal.
- **Settings** live in the database and change only through the admin socket, so only the laptop sets them. The phone's Settings screen is the phone's own: the theme, Ask Claude's model (`airlock.askModel`) and the secret games' sound (`airlock.game.settings`), in its browser's `localStorage`.
- **Dev servers**: your listening ports that look like dev servers or were started from a terminal, each linked to its terminal tab. Previewed through the hub's preview listener on its own origin: it checks the same device and Face ID cookies, proxies (websockets included, for hot reload) only to a current dev server, rewrites Host and Origin to `localhost:<port>`, and strips Airlock's cookies both ways.
- **Themes**: current, Matrix, 8-bit boot, Teletext, handheld console, Game Boy, 90s workstation, vector display, hacker, on the phone only. A theme is a set of design tokens under `<html data-theme>` (`ui/src/styles/themes.css`), a header for the main screens (`ui/src/lib/headers/`) and a layout for the terminal list (`ui/src/features/terminals/home/`); every other screen takes only its tokens. The terminal takes the theme's colours, font and ANSI palette only while `data-terminal="theme"`, and xterm is given a web font only once it has loaded, since it measures the font when set. Moving decorations run only with `data-motion="on"` and outside reduced motion. Fonts are bundled, so the CSP needs no font host. The Game Boy theme wraps the screens in its case (`GameBoyShell.svelte`), whose buttons move focus through what's on screen; a terminal or a preview leaves the case for the whole phone.

- **The secret game** (`ui/src/features/game/`): Hop Count, a platformer that opens from a long press on any screen's header (`door.svelte.ts`, `secretDoor`) or the keyboard code, over the screen or, in the Game Boy theme, in the case's screen, on the case's buttons (`caseButtons`). Only `door.svelte.ts` and `GameHost.svelte` are in the main bundle; `GameHost` imports the rest on first open. The play steps at a fixed 60 a second (`sim.ts`, `physics.ts`, `boss.ts`), levels come from `generator.ts` and the chunks in `chunks.ts`, and `validate.ts` (tests only) checks they can be finished; the buttons of the keys, the screen and the case are merged in `input.ts`. The world map (`world.ts`, drawn by `render.ts`) keeps each hop's record (cleared by its flag or left by its backdoor, its three keys, its best time) and opens hops from it: a flag opens the next hop, and a core's boss or a backdoor the next zone. It comes up after every clear, and from the title and the pause menu; it shows the zones reached and the next one, still shut, and plays any open hop, while the pause menu's Continue carries on the hop in progress. It draws on a canvas 144 pixels tall and 160 to 256 wide, scaled in whole steps, with sprites painted once per theme from the theme's tokens (`skin.ts`, `art.ts`, `sprites.ts`, `render.ts`); sound is `music.ts` and `audio.ts`. It lives inside the unlocked part of the app, so Face ID's lock screen closes it. Closing or hiding it cancels its frame loop, suspends its audio and saves it to `localStorage` (`airlock.game`, the world map's records with it; a save from before the map is brought up to date as it's read, every hop before its own counted as cleared; the mute switch in `airlock.game.settings`), as it also does every five seconds of play.
- **Keepalive, the second secret game** (`ui/src/features/keepalive/`): a top-down story adventure. The same long press or code opens a card to pick a game (`GamePicker.svelte`, the one played last first, remembered in `airlock.games.last`); `GameHost.svelte` loads the card and each game on first use. Echo, a ping, sets out from Loopback with four companions who follow, banter, react and join in: Cron freezes time, Sudo forces walls and heavy blocks, Float hovers over gaps, Tel talks to terminals. A lets the one in front act, the switch button (Select on the case) puts the next in front, and B pings, which lights relays and lamps, stuns bugs and shows what's hidden. Five chapters and a hub town, each with its places, puzzles, boss, song and colours. The story is written in a small line script (`script.ts`; scenes, choices, conditions and effects over flags, trust and the party, compiled by `story.ts` and run by `talk.ts`), and choices move each companion's trust, which opens lines, side quests (`quests.ts`) and decides the ending. The world steps at a fixed 60 a second (`sim.ts`, `bosses.ts`) on 16-pixel tiles (`world.ts`), on the same canvas sizes as Hop Count, painted per theme and chapter from the theme's tokens (`look.ts`, `art.ts`, `paint.ts`, `render.ts`), with Hop Count's synth playing its own songs (`songs.ts`, `../game/music.ts`, `../game/audio.ts`). What's said, the choices, the log and the menus are in the page over the canvas (`KeepaliveOverlay.svelte`); the on-screen pad (`Pad.svelte`) and the keys go through `input.ts`, which tracks each finger and key and lets go of all of them on blur, hiding, a menu or closing, and the case's buttons through `casePad`. The world map (`map.ts`) is worked out from the flags each time it opens: the places been and those an open road leads to, secrets found of all there are, where the story goes next and where side quests wait, and travel to places reached. The engine and the hub town are one chunk; each chapter (`chapters/*.ts`, through `content.ts` and `library.ts`) is another, fetched a chapter ahead. The tests check every scene can be reached and finished, that a tile solver (`solve.ts`) can clear every room with the abilities you have by then and not without the one it is built for, and play the whole story through to each ending. Saves go to `airlock.keepalive` when closed or hidden, at checkpoints and every five seconds of play; it shares Hop Count's sound switch (`airlock.game.settings`), and muted it makes no `AudioContext` at all.
